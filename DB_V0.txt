RELAYFLOW - BASE MONGODB V1
===========================

Ce document définit la nouvelle base MongoDB de RelayFlow.
Il respecte le cahier des charges PDF et les fonctionnalités présentes dans le front.

Terminologie canonique :
- vendeur
- livreur
- manager
- super_manager

Principes généraux
------------------
- Tous les identifiants sont des ObjectId MongoDB.
- Les dates sont des BSON Date en UTC.
- Les montants sont stockés en centimes (entiers), jamais en nombres flottants.
- Les mots de passe sont uniquement stockés sous forme de hash sécurisé.
- Les contrôles de rôle, propriété et juridiction sont appliqués côté serveur.
- Les listes sont paginées côté serveur.
- Les historiques métier sont intégrés aux documents concernés.
- Les suppressions fonctionnelles utilisent des statuts ou deletedAt afin de conserver l'audit.


1. COLLECTION accounts
----------------------
Point d'entrée unique pour l'authentification de tous les acteurs.

{
  _id: ObjectId,
  email: String,
  passwordHash: String,
  role: "vendeur" | "livreur" | "manager" | "super_manager",
  accountStatus: "invite" | "actif" | "suspendu",

  invitation: {
    tokenHash: String,
    expiresAt: Date,
    acceptedAt: Date | null
  } | null,

  failedLoginAttempts: Number,
  lockedUntil: Date | null,
  lastLoginAt: Date | null,
  createdAt: Date,
  updatedAt: Date,
  deletedAt: Date | null
}

Index :
- unique { email: 1 }
- { role: 1, accountStatus: 1 }
- TTL optionnel sur invitation.expiresAt pour une collection d'invitations séparée

Règles :
- vendeur et livreur peuvent s'inscrire eux-mêmes ;
- un manager est créé/invité par un super_manager ;
- le premier super_manager est provisionné directement en base ;
- le JWT contient au minimum sub, role, iat et exp.

{
  _id: ObjectId,

    level: "ville" | "departement" | "pays",

- ville : uniquement la ville affectée ;
- departement : toutes les villes de ce département ;

5. COLLECTION partnerships
--------------------------
Équipe permanente entre un vendeur et un livreur.

{
  _id: ObjectId,
  sellerId: ObjectId,
  courierId: ObjectId,
  status: "en_attente" | "actif" | "revoque" | "rejete",
  invitationMessage: String | null,
  rejectionReason: String | null,
  createdAt: Date,
  respondedAt: Date | null,
  revokedAt: Date | null,
  updatedAt: Date
}

Index :
- unique { sellerId: 1, courierId: 1 }
- { courierId: 1, status: 1 }
- { sellerId: 1, status: 1 }

Règles :
- un livreur peut avoir plusieurs partenariats actifs avec des vendeurs différents ;
- une seule relation est conservée par paire sellerId/courierId et peut être reproposée après rejet ou révocation ;
- seul le livreur concerné peut accepter ou refuser une proposition au statut "en_attente" ;
- accepter une proposition n'annule jamais les autres partenariats du livreur ;
- le vendeur et le livreur sont notifiés à chaque proposition, décision ou révocation.


6. COLLECTION deliveries
------------------------

{
  _id: ObjectId,
  trackingNumber: String,
  sellerId: ObjectId,
  handlingMode: "propre" | "equipe" | "pool_plateforme",
  poolAssignmentMode: "automatique" | "validation_vendeur" | null,

  publicTracking: {
    enabled: Boolean,
    tokenHash: String | null,
    createdAt: Date | null,
    revokedAt: Date | null
  },

  assignedCourierId: ObjectId | null,
  ownDeliveryCourierName: String | null,

  economics: {
    currency: "EUR",
    sellerDeliveryFeeCents: Number,
    courierEarningCents: Number,
    platformCommissionCents: Number,
    pricingRule: "tarif_fixe_plateforme" | "livraison_propre_sans_frais",
    calculatedAt: Date
  },

  customer: {
    firstName: String,
    lastName: String,
    phone: String | null,
    deliveryAddress: {
      line1: String,
      line2: String | null,
      postalCode: String,
      city: String,
      department: String,
      country: String,
      location: {
        type: "Point",
        coordinates: [Number]
      } | null
    }
  },

  contentDescription: String,
  specialInstructions: String | null,
  expectedDeliveryAt: Date,

  status: "SOUMISE" | "ACCEPTEE" | "REFUSEE" | "RETIREE" | "LIVREE" | "ECHOUEE",
  deliveryCodeHash: String | null,

  proof: {
    method: "code" | "photo",
    photoUrl: String | null,
    confirmedAt: Date,
    confirmedByAccountId: ObjectId
  } | null,

  failure: {
    reason: String,
    failedAt: Date,
    failedByAccountId: ObjectId
  } | null,

  attemptNumber: Number,
  submittedAt: Date,
  acceptedAt: Date | null,
  pickedUpAt: Date | null,
  deliveredAt: Date | null,
  createdAt: Date,
  updatedAt: Date,

  history: [
    {
      fromStatus: String | null,
      toStatus: String,
      actorAccountId: ObjectId,
      occurredAt: Date,
      comment: String | null
    }
  ]
}

Index :
- unique { trackingNumber: 1 }
- unique sparse { "publicTracking.tokenHash": 1 }
- { sellerId: 1, status: 1, submittedAt: -1 }
- { assignedCourierId: 1, status: 1, submittedAt: -1 }
- { handlingMode: 1, status: 1, "customer.deliveryAddress.department": 1 }
- { "customer.lastName": 1, "customer.firstName": 1 }
- 2dsphere { "customer.deliveryAddress.location": "2dsphere" }

Transitions autorisées :
- SOUMISE -> ACCEPTEE ou offre refusée par un candidat ;
- ACCEPTEE -> RETIREE ou ECHOUEE ;
- RETIREE -> LIVREE ou ECHOUEE ;
- ECHOUEE -> SOUMISE lors d'une redistribution explicite ;
- LIVREE est terminal.

En mode "propre", la création journalise directement SOUMISE -> ACCEPTEE.
Le refus d'un candidat ne doit pas fermer une offre pool encore disponible pour d'autres livreurs.
Un suivi public n'est résolu que par un jeton opaque actif ; le numéro de suivi seul ne donne aucun accès public.
En pool automatique, une mise à jour atomique attribue la livraison au premier livreur qui accepte.
En pool validation_vendeur, les acceptations des livreurs restent des candidatures jusqu'au choix du vendeur.


7. COLLECTION deliveryOffers
----------------------------
Conserve les offres proposées aux livreurs et leurs refus, sans détourner le statut principal de la livraison.

{
  _id: ObjectId,
  deliveryId: ObjectId,
  courierId: ObjectId,
  source: "equipe" | "pool_plateforme",
  status: "proposee" | "candidate" | "acceptee" | "refusee" | "expiree" | "perdue",
  refusalReason: String | null,
  decisionByAccountId: ObjectId | null,
  outsideCoverageSuggestion: Boolean,
  distanceKmAtOffer: Number | null,
  offeredAt: Date,
  respondedAt: Date | null,
  expiresAt: Date | null
}

Index :
- unique { deliveryId: 1, courierId: 1 }
- { courierId: 1, status: 1, offeredAt: -1 }
- { deliveryId: 1, status: 1 }

Règles :
- en mode automatique, seule la première acceptation conditionnée par deliveries.status = "SOUMISE" gagne ;
- en mode validation_vendeur, seuls les livreurs ayant une offre au statut "candidate" peuvent être choisis ;
- lorsqu'aucune offre n'existe dans une zone couverte, les offres pool hors zone sont classées par distance croissante.

9B. COLLECTION reportMessages
------------------------------
Messagerie interne rattachée aux signalements. Aucun échange par e-mail et aucun
compte client ne participent à ces conversations.

{
  _id: ObjectId,
  reportId: ObjectId,
  senderAccountId: ObjectId,
  recipientAccountIds: [ObjectId],
  content: String,
  readByAccountIds: [ObjectId],
  createdAt: Date,
  editedAt: Date | null,
  deletedAt: Date | null
}

Index :
- { reportId: 1, createdAt: 1 }
- { recipientAccountIds: 1, createdAt: -1 }
- { senderAccountId: 1, createdAt: -1 }

Règles :
- contenu nettoyé et limité à 1 000 caractères ;
- un manager ne peut écrire qu'aux vendeurs et livreurs réellement liés au dossier ;
- un vendeur ou livreur concerné peut répondre au manager assigné ;
- le super_manager peut participer aux dossiers escaladés ou supervisés ;
- le client n'est jamais destinataire car il ne possède pas de compte ;
- chaque message crée une notification interne dans la même transaction ;
- les droits de lecture sont recalculés côté serveur à chaque requête ;
- aucune adresse e-mail ni donnée d'un autre dossier n'est exposée.

Demandes d'inscription des vendeurs et livreurs, traitées par les managers.

  reference: String,
  accountId: ObjectId,
  profileId: ObjectId,
  role: "vendeur" | "livreur",
  displayName: String,
  emailSnapshot: String,
  phoneSnapshot: String,
  addressSnapshot: String,
  postalCode: String,
  city: String,
  cityCode: String,
  department: String,
  departmentCode: String,
  vehicleType: String | null,
  documentIds: [ObjectId],
  status: "en_attente" | "acceptee" | "rejetee",
  assignedManagerIds: [ObjectId],
  fallbackAllManagers: Boolean,
  decidedByManagerId: ObjectId | null,
  decisionComment: String | null,
  decidedAt: Date | null,
  history: [{
    status: String,
    actorAccountId: ObjectId | null,
    comment: String,
    occurredAt: Date
  }],
  createdAt: Date,
  updatedAt: Date
}

Index :
- unique { reference: 1 }
- unique partiel { accountId: 1, status: 1 } pour status = "en_attente"
- { assignedManagerIds: 1, status: 1, createdAt: -1 }
- { city: 1, status: 1, createdAt: -1 }
- { emailSnapshot: 1, createdAt: -1 }

Règles :
- les champs obligatoires, l'e-mail et le téléphone sont validés côté serveur ;
- le téléphone est stocké sous une forme normalisée et formaté pour l'affichage ;
- si un manager possède une juridiction de niveau ville correspondant exactement à city,
  la demande lui est attribuée ;
- si aucun manager de ville ne correspond, assignedManagerIds contient tous les managers actifs ;
- seul un manager présent dans assignedManagerIds peut accepter ou rejeter la demande ;
- l'acceptation, l'activation de accounts et la création éventuelle de l'abonnement vendeur
  sont réalisées dans une transaction MongoDB ;
- le refus laisse une trace d'audit et rend le compte inutilisable ;
- les justificatifs sont stockés hors MongoDB dans un stockage objet privé ; la collection ne
  contient que leurs identifiants, métadonnées et empreintes ;
- les réponses API n'exposent jamais passwordHash, document privé ou historique non autorisé.


CONTRAINTES APPLICATIVES IMPORTANTES
====================================

1. Propriété
- un vendeur accède uniquement à son profil, ses partenariats, livraisons, factures et signalements ;
- un livreur accède uniquement à son profil, ses offres, livraisons assignées, bons et signalements.

2. Juridiction
- toutes les requêtes Manager appliquent la juridiction côté serveur avant le retour des données ;
- aucune donnée hors juridiction ne doit être envoyée au navigateur ;
- un Super Manager a une vision globale.

3. Éligibilité des offres
- statut livreur = disponible ;
- zone du livreur compatible avec la livraison ;
- mode equipe : partenariat actif obligatoire ;
- mode pool_plateforme : offre ouverte aux livreurs éligibles ;
- le premier livreur qui accepte obtient la livraison via une opération atomique.

4. Livraison
- toute transition est validée par la machine à états ;
- retrait et remise ne peuvent être confirmés que par le livreur assigné ;
- remise confirmée par code valide ou photo justificative ;
- motif obligatoire en cas d'échec ou de refus ;
- redistribution explicite après échec, avec incrément du numéro de tentative.

5. Finance
- devise unique configurée dans platformSettings ;
- facture vendeur = abonnement mensuel fixe + frais fixes des livraisons LIVREE en equipe ou pool ;
- une livraison propre apparaît à 0 centime dans le détail et ne génère aucune charge livreur ;
- bon livreur calculé sur les livraisons LIVREE réellement assignées ;
- paiements constatés manuellement, sans paiement en ligne dans ce périmètre.

6. Sécurité
- hash Argon2id ou bcrypt pour les mots de passe ;
- hash des tokens d'invitation et codes de livraison ;
- JWT court transmis par Authorization: Bearer ;
- limitation des connexions ;
- validation systématique des écritures ;
- journalisation des actions Manager et Super Manager.

7. Pagination et recherche
- pagination par curseur ou page/limit borné ;
- recherche livraison par trackingNumber ou nom/prénom client ;
- filtres date, période, zone, vendeur, livreur et statut ;
- index adaptés aux écrans de tableaux de bord et aux listes.

CONTRAT API ET AGRÉGATIONS DES TABLEAUX DE BORD
==============================================

Le front ne doit pas fabriquer de séries statistiques. L'API calcule les chiffres dans la juridiction
et la période autorisées, puis renvoie un modèle prêt à afficher.

Temps réel et cohérence :
- toute création ou transition importante produit un événement métier après validation en base ;
- MongoDB Change Streams ou une table d'outbox alimente un canal WebSocket/SSE authentifié ;
- les événements sont filtrés côté serveur par compte, rôle et juridiction avant diffusion ;
- événements principaux : registration.created, registration.decided, delivery.created,
  delivery.assigned, delivery.status_changed, invoice.created, invoice.paid,
  payment_voucher.created, payment_voucher.paid et report.updated ;
- le client invalide alors les requêtes concernées et recharge les totaux depuis l'API ;
- l'acceptation d'une livraison utilise une mise à jour atomique conditionnée par status = "SOUMISE"
  afin qu'un seul livreur puisse l'obtenir ;
- une notification et l'écriture métier correspondante sont créées dans la même transaction,
  puis l'envoi push est repris de manière asynchrone et idempotente ;
- les tableaux financiers sont reconstruits depuis invoices, paymentVouchers, subscriptions
  et deliveries, jamais depuis des valeurs visuelles locales.

GET /api/dashboard?months=6

Réponse :
{
  totals: {
    deliveries: Number,
    submitted: Number,
    active: Number,
    delivered: Number,
    openReports: Number,
    sellers: Number,
    couriers: Number,
    unpaidInvoicesCents: Number,
    courierBalanceCents: Number
  },
  series: {
    labels: [String],
    deliveries: [Number],
    delivered: [Number],
    reports: [Number],
    invoicesCents: [Number],
    paymentsCents: [Number]
  },
  generatedAt: Date
}

Pipeline livraisons par mois :
- $match sur sellerId/courierId/juridiction et intervalle de dates ;
- $dateTrunc de submittedAt avec unit = "month" ;
- $group par mois et statut ;
- remplissage serveur des mois sans résultat avec la valeur 0.

Pipeline signalements par mois :
- $match sur assignedManagerId ou périmètre global du super_manager ;
- $dateTrunc de createdAt avec unit = "month" ;
- $group par mois et status ;
- aucun filtrage géographique ne doit être effectué uniquement dans le navigateur.

Pipeline financier :
- invoices groupées par issuedAt et status ;
- paymentVouchers groupés par issuedAt et status ;
- sommes calculées en centimes.

Chaque réponse de liste contient :
{
  data: [],
  pagination: {
    page: Number,
    limit: Number,
    total: Number,
    totalPages: Number
  }
}

La couche d'accès du front consomme ces contrats et expose les mêmes objets aux composants.
Le store local de démonstration doit rester un adaptateur de remplacement et produire exactement
la même forme de données que l'API MongoDB.

Validation backend obligatoire :
- listes blanches pour les champs de tri, filtres, statuts et transitions ;
- conversion stricte des identifiants avec ObjectId.isValid avant toute requête ;
- interdiction d'accepter directement un objet MongoDB venant du navigateur ;
- rejet des clés commençant par "$" ou contenant "." ;
- construction serveur des filtres MongoDB, sans fusion libre de req.body ;
- schémas de validation stricts avec champs inconnus refusés ;
- échappement et longueur maximale des recherches textuelles ;
- pagination bornée ;
- réponses sans passwordHash, tokenHash, codeHash ou données hors juridiction ;
- requêtes atomiques pour l'acceptation d'une livraison et les transitions d'état.
